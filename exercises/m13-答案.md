# M13 习题答案：推理的数学与模型格式

> 对应 [m13-习题](m13-习题.md)。

## A 概念题

1. Prefill 处理整段 prompt，是大 GEMM，计算密集；decode 每步只来 1 个 token，是瘦 GEMM，带宽密集。同一个模型，prefill 的算术强度高，decode 的算术强度低，所以瓶颈从算力切到带宽。
2. TTFT 是首 token 延迟（prefill 为主）；TPOT/ITL 是每输出 token 延迟（decode 为主）；吞吐是每秒总 token 数；goodput 是满足 SLO 的有效吞吐。例子：batch=64 时总吞吐很高，但每个请求 TPOT 很长，用户等一个字要几百毫秒。
3. 量化只减少字节，不减少 FLOPs；收益上限是“省下的字节 ÷ 总读取字节”。短上下文时权重占大头，KV 量化收益小；长上下文时 KV 占大头，收益才明显。
4. PagedAttention 用 block 管理 KV，减少显存碎片；prefix cache 复用相同前缀的 KV，减少重复 prefill。它们提高显存利用率和吞吐，但不改变单请求的矩阵乘/带宽数学。
5. 当模型在支持列表、硬件匹配、内存层级复杂（MoE/长上下文/SSD）、你接受窄支持时值得选。反例：用 24 GB 卡跑 1.7B dense 模型，llama.cpp/Ollama 更稳，专用引擎的额外复杂度没有收益。

## B 计算题

1. $2\cdot32\cdot8\cdot128\cdot32768\cdot2/2^{30}=4$ GiB；$H_{kv}=32$ 时是 16 GiB，省 12 GiB（4 倍）。
2. global：$2\cdot6\cdot4\cdot128\cdot131072\cdot2/2^{30}=1.5$ GiB；SWA 约 2.5 MiB；合计约 1.5 GiB。
3. 读取 $14+16=30$ GiB；$30/2000=15$ ms/token；$1000/15\approx67$ token/s。
4. 78 GiB → 46 GiB；$78/2000=39$ ms → $46/2000=23$ ms。
5. 活跃权重约 $5\times10^9\times0.5=2.5$ GB；$5/2.5=2$ token/s 上限。还要加上 shared experts、attention、KV、PCIe/内存拷贝、路由开销，实际会更低。

## C 场景题

1. 先 `ollama ps` 或 `/api/ps` 看 `context_length`；再看日志有没有 `truncating input prompt` / `slot context shift`；然后把 `num_ctx` 提到 64k/128k，`num_keep` 设到 system prompt 长度；最后用 llama.cpp 加 `--no-context-shift` 对照。因为 32k 正好是 Ollama 在 24–48 GB 显存档位的默认值，先排除配置/截断，再怀疑模型。
2. A：Qwen3.8-27B 在 24 GB 卡上优先 HyperQwen（vLLM 补丁，150k context）；也可 llama.cpp + 量化。B：Qwen3.8-Flash-Next 是百B MoE，24 GB 卡优先 Strata/colibri/ds4；关键约束是 RAM、磁盘和专家缓存，不是显卡算力。
3. 多用户看吞吐、并发、SLA、PagedAttention/prefix cache、TP/PP、监控与鉴权 → vLLM/SGLang；个人单机看延迟、易用性、上下文控制 → llama.cpp/Ollama。8×H100 的选型不是“哪个 tok/s 高”，而是“在 SLO 下能服务多少并发”。

## D 开放题

1. Baseline：fp16 KV；变量：int8/int4、per-tensor/per-group、不同序列长度（4k/32k/128k）；指标：显存、TPOT、吞吐、长文任务准确率/困惑度；控制：同一模型、同一 prompt、同一 batch、同一硬件；失败判据：长文准确率掉超过阈值，或 kernel 不支持导致实测无收益。
2. 例：12 GB 显卡放 attention/shared experts/hot experts；64 GB 内存放全部专家；NVMe 放冷专家/ngram。按活跃 5B、4-bit 约 2.5 GB/token，若有效带宽 3–5 GB/s，上限约 1–2 token/s；实际受路由、PCIe、内存带宽影响。分层目标是让热专家命中率足够高，避免每 token 都读磁盘。

## E 13.2 概念题

1. GGUF 是容器，量化是容器里的 tensor 怎么表示；同一个 GGUF 可以是 F16、Q8_0、Q4_K_M、IQ2_XS。
2. 有效 bpw = 文件字节 × 8 / 参数量；多出来的是 scale/zero、混合精度（部分 Q6_K）、metadata/对齐。
3. 权重误差被所有 token 共享；KV 误差随上下文累积，长文任务更敏感。FP8 KV 通常较稳，int8/q4 要测 needle-in-haystack。
4. ① 有对应反量化/矩阵乘 kernel；② 反量化开销不吃掉带宽收益；③ prefill 不是算力受限。缺一个，低 bit 就可能不加速。
5. EXL2：NVIDIA 单用户、ExLlama 内核；NVFP4：Blackwell + TRT-LLM/vLLM；MLX 4-bit：Apple Silicon + MLX。

## F 13.2 计算题

1. $1.10\times10^9\times8/(1.73\times10^9)\approx5.1$ bpw。
2. $14/4=3.5$×；Q4_K_M 实际约 4.8–5.1 bpw，还有 scale/混合精度/元数据。
3. FP16 16 GiB；FP8 8 GiB；q4 4 GiB。
4. FP16：$14+16=30$ GiB，$30/2000=15$ ms；FP8：$14+8=22$ GiB，$22/2000=11$ ms。
5. 活跃权重约 $5\times10^9\times0.5=2.5$ GB；$5/2.5=2$ token/s 上限；实际还要加 shared experts、KV、PCIe/路由开销。

## G 13.2 场景题

1. Q4_K_M + FP8 KV：约 4 GB + 8 GiB ≈ 12 GiB，留出并发/碎片余量；Q8_0 + FP16 KV 约 23.5 GiB，24 GB 卡几乎不能开并发。
2. 先看能不能放下：IQ2/IQ3 最省，NVFP4 需要 Blackwell 软件栈，EXL2 主要 NVIDIA 单用户且不能跨运行时；关键约束是 RAM/SSD/专家缓存，不是单纯显存。
3. H100 上 FP8 有原生 tensor core/kernel，精度和吞吐平衡好；Q4_K_M 更适合显存/带宽受限的单机或边缘。若模型太大、FP8 放不下，才退到 Q4。

## H 13.2 开放题

1. Baseline：F16 权重 + FP16 KV；变量：Q8/Q5/Q4/Q2、AWQ/GPTQ、KV FP8/int8/q4；指标：困惑度、长文 QA/needle、TTFT/TPOT、显存、吞吐；控制：同模型、同 prompt、同 batch、同硬件；失败判据：长文准确率掉超过阈值，或 kernel 不支持导致无收益。
