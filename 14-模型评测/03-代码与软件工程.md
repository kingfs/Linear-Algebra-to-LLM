# 14.3 代码与软件工程：从 HumanEval 到 Terminal-Bench

> **本节位置**：模块 14 · 模型评测 ｜ **前置**：[14.1 评测的数学](01-评测的数学.md) ｜ **预计**：55 分钟
>
> **一句话**：代码评测在两年里走完了四级台阶——**写函数 → 做竞赛题 → 修真实 issue → 在终端里干完整活**；每上一级，题目更真、脚手架更重、分数更难比。

## 0. 场景引入

> **数据口径**：本页出现的 2026 年模型分数为教学示例、未独立核验，不得作为事实引用；以各模型官方卡片与基准官方榜单为准（见 [M14 口径说明](README.md)）。

把三张 2026 年的发布表放在一起，你看到：

- Qwen3.8-27B：Terminal-Bench 2.1（Terminus）**73.0**，SWE-bench Pro **61.7**，DeepSWE 1.1 **42.2**；
- LFM3-1.7B：Terminal-Bench 2.1（OpenCode）**12.92**，SWE-bench Verified（OpenCode）**43.40**，LiveCodeBench v6 **73.46**；
- DeepSeek-V4.1-Flash-1017：Terminal-Bench **4.0** **42.3**，DeepSWE v1.1 **77.0**，ProgramBench **29.1**。

这些数字放在一起，几乎可以拼出所有误读：

1. “LFM3 的 SWE-bench Verified 43.40，比 Qwen 的 SWE-bench Pro 61.7 低”——**两个 benchmark，不能比。**
2. “DeepSeek 的 42.3 比 Qwen 的 73.0 低”——**4.0 和 2.1，不能比。**
3. “LFM3 的 LiveCodeBench 73.46 与 Qwen 的 90.3 能不能直接比？”——**能，因为题集相同；但它只说明竞赛题，不说明仓库任务。**
4. “Qwen 的 TB2.1 两个 harness 差多少？”——卡片只给了一个 harness，另一个得自己跑。

**这一节要做的，是把“代码评测”拆成四条赛道，并说清每条赛道的分数为什么不能混。**

## 1. 直觉

把代码能力想成四种工作现场：

| 现场 | 你被要求做什么 | 像什么 | 代表 |
| --- | --- | --- | --- |
| 函数题 | 补全一个函数，跑几个单测 | 课后作业 | HumanEval、MBPP |
| 竞赛题 | 现场读题、写算法、过隐藏用例 | 编程比赛 | LiveCodeBench、Codeforces |
| 修 issue | 进一个陌生仓库，读代码、改多处、过测试 | 上班修 bug | SWE-bench 家族 |
| 终端任务 | 给你一台机器，自己装环境、跑命令、交付 | 外包接活 | Terminal-Bench、ProgramBench、NL2Repo |

台阶越高，**“模型能力”占的比重越小，“脚手架 + 环境”占的比重越大**。到终端任务，同一个模型换个 harness 差 20 分不稀奇。

这个类比在哪里失效：真实上班可以问同事、可以查文档、可以拖到明天；benchmark 有固定的步数、超时和容器。**它测的是“在受限环境里能不能交付”，不是“真实工期里的表现”。**

## 2. 定义

### 2.1 四条赛道与指标

| 赛道 | 任务形态 | 判分 | 主指标 | 常见规模 |
| --- | --- | --- | --- | --- |
| 函数级 | 给签名 + docstring，补函数 | 单元测试 | pass@1 | 164（HumanEval）、374（MBPP） |
| 竞赛级 | 给题面，写完整程序 | 隐藏用例 | pass@1、Elo | [LiveCodeBench](#ref-jain-2024)、Codeforces |
| issue 修复 | 给仓库 + issue，提 patch | 仓库测试 | resolve rate | 500–2,000+ |
| 终端/仓库 | 给环境 + 目标，自己干活 | 最终状态、测试、行为 | pass rate、resolved | 74–200+ |

四条赛道之外还有一条**横切赛道**：科学计算代码（SciCode）。它跨在“函数级”与“竞赛级”之间，但判分靠子问题的数值/物理测试，见 §4.5。

### 2.2 harness 是什么

harness 是“替模型动手的那套程序”：它决定模型能看到什么、能调用哪些工具、能走多少步、怎么提交。

同一个模型，不同 harness 的差别包括：

- 文件编辑方式（整文件重写 vs patch）；
- 命令执行与反馈（有没有 shell、能不能装包）；
- 上下文管理（历史怎么截断、要不要总结）；
- 步数/超时/预算；
- 提交与重试规则。

**所以“模型分数”从来不是模型的裸能力，而是“模型 × harness × 环境”的联合成绩。**

### 2.3 四个关键指标

- **pass@1**：一次成功；最接近用户体验。
- **resolve rate**：SWE-bench 里“测试通过”的比例；等价于 pass@1 的一种。
- **avg@n**：跑 $n$ 次取平均；降低方差，但成本 ×n。
- **pass@k**： $k$ 次里至少一次成功；衡量“有没有这个能力”，不是“稳不稳”。

## 3. 为什么这样定义

每一代 benchmark 都是对上一代漏洞的补丁：

| 上一代的问题 | 下一代怎么补 | 代价 |
| --- | --- | --- |
| HumanEval 太短、可背 | LiveCodeBench 用带发布日期的竞赛题 | 题源受赛事周期限制 |
| 竞赛题只考算法 | SWE-bench 用真实 issue + 仓库测试 | 依赖环境、测试可能不全 |
| SWE-bench 题目泄漏、测试过严 | Verified 人工复核 500 题 | 仍然公开、仍会饱和 |
| Verified 饱和 | Pro 换私有/持份代码、加难度 | 分数骤降、复现成本高 |
| Pro 的继承测试可被绕过 | DeepSWE 手写 verifier、题目不回馈上游 | 规模小（113 题） |
| 修 bug 不等于从零建 | NL2Repo、ProgramBench 要求“从规格/二进制重建” | 分数极低、评测贵 |
| 单轮修 bug 不等于长程工作 | Terminal-Bench 用真实终端、多容器、GPU | harness 影响巨大 |

**这条链条说明：代码评测的演化不是“越来越难”，而是“越来越像真实交付”。**

## 4. 性质与推导

### 4.1 SWE-bench 家族谱系

| 名称 | 时间 | 题目 | 关键变化 | 读法 |
| --- | --- | --- | --- | --- |
| [SWE-bench](#ref-jimenez-2024-coding) | 2023-10 | 2,294 个 issue、12 个仓库 | 真实 issue + 仓库测试 | 开山之作，已偏饱和 |
| SWE-bench Verified | 2024-08 | 500 题 | 人工确认“可解、测试可靠” | 2024–2025 的事实标准 |
| SWE-bench Multimodal | 2024-10 | 带图/前端的 JS 仓库 | 视觉 + 代码 | 多模态代码的前身 |
| SWE-bench Multilingual | 2025 | 多语言仓库 | 语言覆盖 | 看语言子集，不看总分 |
| [SWE-bench Pro](#ref-scale-2025) | 2025-09 | 1,865 题、41 仓库 | 公共/留出/商业三档；平均改 107.4 行、4.1 个文件 | 难度陡增，2026 仍在用 |
| SWE-bench Pro V2 | 2026-10 | 642 题 + 51 题 Hard | 修复/退役 480/731 题；防联网取补丁 | 公开集又被推到 99.4%，看 Hard |

一个反直觉的事实：**Pro V2 修完题之后，前沿 agent 在公开集上能到 99.4%**。这说明“修得越干净，饱和得越快”；于是竞争转向 51 题的 Hard split 和私有商业集。

### 4.2 Terminal-Bench 的语义化版本

[Terminal-Bench](#ref-tbench-2026) 把 benchmark 当软件维护，用语义化版本：

| 版本 | 时间 | 变化 | 能不能和上一版比 |
| --- | --- | --- | --- |
| 1.0 | 2025-05 | 初版 | — |
| 2.0 | 2025-11 | 89 题，标准化容器 | 不能 |
| 2.1 | 2026-05 | 修 28 题（依赖漂移、资源不足、题面与测试不符） | 不能，需重跑 |
| 3.0 | 2026-07 | 74 题、7 领域，多容器/GPU，最佳约 34% | 不能 |
| 4.0 | 2026-08 | 资源校准、删 8 题、修 19 题、统一 8 小时超时 | 不能，major 变更 |

官方规则：**主版本变 = 必须重跑；次版本变 = 可重新判分；补丁版本 = 可复用结果。** 这比“v2 一定比 v1 难”的直觉更可靠。

### 4.3 为什么 harness 能拉开 20 分

以 Terminal-Bench 2.1 的公开数据为例：

- GPT-5.3-Codex + Codex CLI：73.3 → 79.1；
- Opus 4.6 + Claude Code：58.0 → 70.1（+12.1）；
- GPT-5.4 + Terminus 2：55.1 → 54.8（−0.2）；
- Gemini 3.1 Pro + Terminus 2：63.0 → 70.7（+7.6）。

同一代模型，换 harness 的增益可以从 −0.2 到 +12.1。**89 题的抽样误差约 ±10 pp（ $p\approx0.6$），所以 12 分的 harness 差异已经接近“可检测”，而 2–3 分的模型差异基本不可检测。**

### 4.4 测试泄漏与 reward hacking

SWE-bench 式评测有三个可攻击点：

1. **题目泄漏**：issue、PR、讨论都在 GitHub 上，模型可能背过。
2. **测试可读**：模型能读测试文件，针对测试写特判。
3. **环境可绕**：联网 clone 上游修复、pip 装现成包、改测试文件。

对应的防守：

- [DeepSWE](#ref-deepswe-2026)：题目原创、不回馈上游、手写 verifier；
- Pro V2：限制网络到模型端点、干净容器重判；
- NL2Repo 的评测中禁用 `pip download/install`、`git clone` 等“取答案”命令；
- ProgramBench：只给可执行文件、禁止反编译、断网。

一个可检验的对照：DeepSWE 的独立 judge 与自家 verifier 的分歧率是 **1.4%**，而 SWE-bench Pro 继承测试的分歧率是 **32.4%**。**“测试通过”不等于“任务完成”，这就是 verifier 设计的价值。**

### 4.5 科学计算代码：SciCode 与“子问题”

[SciCode](https://arxiv.org/abs/2407.13168)（2024）问的不是“会不会写函数”，而是“能不能把一篇论文里的方法写成能跑的代码”：

- 80 道主问题、338 道子问题，由 16 个自然科学子领域（数学、物理、化学、生物、材料……）的科学家出题；
- 每道主问题被拆成若干子问题，**逐个子问题跑单元测试**；
- 判分因此有两层：**子问题通过率**（哪一步断了）与**主问题解决率**（整条链跑通）。

这个两层结构是它最有价值的地方。普通代码题只告诉你“对/错”，SciCode 告诉你“公式写对了、单位错了、边界条件漏了”——科学代码的 bug 大多是数值与物理约束问题，不是语法问题。

一个读表细节：**卡上常写 “SciCode (Inspect AI)”**。Inspect AI 是英国 AISI 的开源评测框架，括号表示“用哪套 harness 跑的”。同一题集、不同框架或不同依赖版本，子问题通过率会变；所以看 SciCode 分数，先确认是主问题还是子问题口径。

数字示例：Ripple-65B 39.4（Inspect AI），同表 Nemotron 44.6、Inkling 46.1、Beam 49.2、Muse 58.5。**它在这张卡上垫底**；但 80 题规模下标准误约 5.5 pp，39.4 与 44.6 在统计上分不开——真正拉开的是 Muse 的 58.5。

## 5. 例子

### 5.1 手算：两个 harness 的差距显著吗

TB 2.1 有 89 题，设 $p\approx0.6$， $\mathrm{SE}=\sqrt{0.24/89}\approx5.2$ pp，95% CI 约 ±10.2 pp。Claude Code 70.1 与 Terminus 63.8 差 6.3 分，**在单次运行的噪声内**；但同一个 harness 下 2.1 相对 2.0 的 +12.1 是配对比较，方差更小，所以更可信。

### 5.2 场景：43.40 与 61.7 能不能比

不能。SWE-bench Verified 是 500 道“确认可解”的题，SWE-bench Pro 是 1,865 道更难、含私有代码的题。**同一个模型在两者之间掉 20–40 分是常态**；跨模型跨基准比较，等于拿小学卷 95 分和高考卷 60 分比。

### 5.3 场景：LiveCodeBench 为什么能跨模型比

因为题集、题源、判分相对统一，且按时间滚动更新，污染可控。LFM3-1.7B 的 73.46 与 Qwen3.8-27B 的 90.3 都是 v6，**这个比较有意义**：它告诉你“小模型在竞赛题上已经能到 73，但在终端任务上只有 12.92”。

### 5.4 场景闭环：代码 agent 选型

- 输入：仓库语言、任务类型（补全/修 bug/搭新项目）、可用的 harness。
- 计算：函数级看 LCB；修 bug 看 Verified/Pro；长程交付看 TB；从零建看 NL2Repo/ProgramBench。
- 输出：不是“总分”，而是“在我的仓库上，用我的 harness，成功率与成本”。
- 失败判据：公开集高、私有集低 → 过拟合；pass@1 低但 pass@8 高 → 需要重试机制；成本/成功任务高于人工 → 不划算。

## 6. 常见误区

1. **“HumanEval 90 分，说明会写代码。”** HumanEval 只有 164 题、函数级、公开多年；90 分在 2026 年说明不了仓库级能力。
2. **“SWE-bench Verified 高，就能干活。”** Verified 是“修一个已定位的 issue”，不是“从零建项目”，也不是“在终端里装环境”。
3. **“都叫 Terminal-Bench，可以放一张表。”** 2.1 与 4.0 题集、资源、超时都变了；官方明确要求 major 变更重跑。
4. **“in-house benchmark 的分数也能对外比较。”** QwenSWEBench、CoWorkBench 这类内部集没有公开题，无法复现，只能当“自评”。
5. **“pass@8 高，产品就稳。”** 产品通常只调用一次；该看 pass@1 或 pass^k。
6. **“SciCode 39 分，说明不会做科研代码。”** 它量的是“从论文方法到可跑代码”的整条链；子问题通过率通常高得多，要看断在哪一步。

## 8. 通往大模型

代码评测之所以成为 2025–2026 的主战场，有三个原因：

1. **可验证**：测试通过/不通过是二值的，比 LLM judge 稳。
2. **可计价**：token、步数、美元成本都能算，直接对应商业价值。
3. **可长程**：一个 issue 要几十到几百步，正好压测“规划 + 执行 + 自检”。

于是模型卡的重心从“HumanEval 多少分”移到“在什么 harness 下、花多少美元、完成多少真实任务”。一个可检验的结论：**当一张卡同时报 TB、SWE-bench Pro、DeepSWE 时，它想说的不是“我会写函数”，而是“我能当 coding agent”；这时你要看的是 harness、成本与私有集，而不是单个最高分。**

## 9. 练习

1. **概念题**：SWE-bench、Verified、Pro、Pro V2、DeepSWE 各自补了上一代的什么漏洞？
2. **计算题**：TB 2.1 共 89 题，模型 A 通过 62 题、B 通过 58 题，求两者准确率与差值的 95% CI；差距显著吗？
3. **计算题**：某 agent pass@1=40%，独立同分布假设下 pass@5 是多少？若实际 pass^5 只有 0.5%，说明什么？
4. **开放题**：为你的团队设计一个“代码 agent 验收方案”，至少覆盖函数级、issue 级、终端级三层，并写出每层的 harness、题源、成本上限。
5. **概念题**：SciCode 的子问题通过率与主问题解决率分别说明什么？为什么科学代码的测试不能只查语法？

## 10. 一页速记

- 四赛道：函数 → 竞赛 → issue → 终端/仓库；越往后越依赖 harness。
- SWE-bench 家族：原版 → Verified（500）→ Pro（1,865）→ Pro V2（642 + Hard）→ DeepSWE（113 原创）。
- Terminal-Bench 用语义化版本：major 变必须重跑。
- SciCode：80 主问题 / 338 子问题，看子问题断点；括号里的 Inspect AI 是 harness。
- 测试通过 ≠ 任务完成；verifier 设计决定分数含金量。
- 比代码分数，先比“同题集、同 harness、同预算”。
