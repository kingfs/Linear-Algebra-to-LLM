# 13.4 调度与并发：batching、KV 与 SLA

> **本节位置**：模块 13 · 从模型到服务 ｜ **前置**：[13.1 推理的数学](01-推理的数学.md)、[13.3 引擎解剖](03-引擎解剖.md) ｜ **预计**：50 分钟
>
> **一句话**：并发不是“同时跑很多请求”，而是**在有限 KV 里，用 batching 和排队，把吞吐与延迟做一个可解释的交换**。

## 0. 场景引入

你的内网 API 上线了：8×H100，7B 模型，32k 上下文，OpenAI 兼容。第一天 10 个人用，很流畅；第二天 64 个人同时用，P95 从 2 秒涨到 40 秒，GPU 利用率却只有 60%。

你去看日志：

- 有些请求在排队（queue time 很长）；
- 有些请求被抢占/重算（preempted）；
- 有些请求的 KV 被换出（swapped）；
- 有些请求的前缀明明一样，却重新 prefill 了一遍。

**问题**：为什么 GPU 没满，用户却觉得慢？为什么 batch 开到 64，吞吐没有变成 64 倍？为什么“加卡”不一定能救 P95？

这一节把并发拆成四个可算的东西：**KV 预算、batch、队列、SLO**。

## 1. 直觉

把 GPU 想成一辆公交车：

- **权重**是司机，开一趟车（一次前向）成本固定；
- **batch** 是车上的乘客，乘客越多，司机成本摊得越薄；
- **KV** 是乘客的行李，行李太多，车装不下；
- **调度器**是车站调度，决定谁先上车、要不要等下一班；
- **SLO** 是“乘客最多等 5 分钟”的承诺。

关键洞察：

- 多载客（大 batch）能提高“每公里运力”，但会让单个乘客绕路（TPOT 变长）；
- 行李（KV）决定车能装多少人；
- 如果乘客到得比车快，就会排队；如果车到得比乘客快，就空转。

> 💡 **一句话直觉**：**吞吐是“车能运多少人/小时”，延迟是“一个人等多久”；两者由 KV 和调度同时决定。**

这个类比在哪里失效：公交车可以无限等，推理请求有超时；公交车的行李不随路程增长，KV 随上下文线性增长；公交车加一辆就多一份运力，推理加卡要过通信/并行。

## 2. 定义

### 2.1 两种 batching

- **静态 batching**：攒够 $B$ 个请求，一起 prefill/decode，等最慢的结束再走下一批。简单，但短请求会被长请求拖住。
- **连续 batching（continuous batching）**：每个 decode step 都可以加入新请求、移除完成请求；GPU 不等整批结束。[vLLM](#ref-vllm-docs-2026)/[Orca](#ref-yu-2022) 的核心。

### 2.2 请求状态

| 状态 | 含义 |
| --- | --- |
| waiting | 排队，等 KV/调度 |
| running | 在 decode batch 里 |
| swapped | KV 被换到 CPU/其他池 |
| preempted | 被抢占，稍后重算/恢复 |
| finished | 完成/取消/超时 |

### 2.3 指标

| 指标 | 含义 | 注意 |
| --- | --- | --- |
| TTFT | 首 token 延迟 | 受 queue + prefill 影响 |
| TPOT/ITL | 每输出 token 延迟 | 受 batch/KV 影响 |
| P50/P95/P99 | 延迟分位数 | 平均会骗人 |
| throughput | 总 token/s | 高吞吐可能牺牲单请求 |
| goodput | 满足 SLO 的吞吐 | 生产真正该看 |
| SLO/SLA | 服务目标/协议 | 例如 P95 TPOT ≤ 50 ms |

### 2.4 前缀缓存

如果多个请求共享相同的 system prompt/RAG 文档，引擎可以复用它们的 KV，避免重复 prefill。[vLLM](#ref-vllm-docs-2026) 的 prefix caching、[SGLang](#ref-zheng-2023) 的 RadixAttention 都在做这件事。

## 3. 为什么这样定义

因为并发系统里，**吞吐和延迟不是一回事**：

- 单请求：看 TPOT，GPU 可能大量空转；
- 多请求：batching 提高吞吐，但 TPOT 变长；
- 超过 KV 预算：排队/抢占，P95 爆炸；
- 前缀重复：不算清楚命中率，就会重复做 prefill。

如果只看“GPU 利用率”，会误判：利用率 60% 可能是因为 KV 不够、batch 上不去；也可能是因为请求在排队，GPU 在等调度。**必须同时看 queue、KV、batch、TTFT/TPOT 分位数。**

## 4. 性质与推导

### 4.1 Little 定律：并发 = 到达率 × 延迟

$$
L=\lambda W
$$

- $L$：系统里的平均请求数；
- $\lambda$：到达率（req/s）；
- $W$：平均停留时间（s）。

例子：10 req/s，平均 5 s，系统里平均 50 个请求。如果你的 KV 只能同时驻留 8 条，剩下的就会排队/换出——**这就是“GPU 没满但很慢”的常见原因**。

### 4.2 KV 预算决定最大并发

$$
B_{\max}\approx \frac{\text{KV budget}}{\text{KV per sequence}}
$$

7B、32k、FP16：每序列约 16 GiB。80 GB 卡扣掉权重/激活，假设 KV 预算 64 GiB：

$$
B_{\max}\approx 64/16=4
$$

所以“64 并发”在 32k 上下文下不可能同时 decode；只能排队、分批、或换更小上下文/量化 KV。

### 4.3 batching 的吞吐与 TPOT

$$
\text{throughput}\approx \frac{B}{\text{TPOT}(B)},\qquad
\text{TPOT}(B)\approx \frac{W+B\cdot KV_{\text{seq}}}{\text{BW}}
$$

$B$ 增大，权重被摊薄，吞吐上升；但 $B\cdot KV$ 也增大，TPOT 变长。存在一个“吞吐-延迟”最优点，不是越大越好。

### 4.4 PagedAttention 的 block 账

[PagedAttention](#ref-kwon-2023) 把 KV 切成固定大小 block（如 16 token），每个序列占 `ceil(T/16)` 个 block。好处：

- 不需要连续大块显存，减少碎片；
- 可以按需增长，不用预留最大上下文；
- 前缀相同的 block 可以共享。

代价：block 表、寻址、copy-on-write 的复杂度；短序列可能有内部碎片。

### 4.5 前缀缓存的收益

设前缀命中率 $h$，完整 prefill 时间 $T_p$：

$$
T_{\text{prefill}}\approx (1-h)\cdot T_p
$$

RAG 场景里，system prompt + 文档可能占 80–95% 的 prompt；命中后 TTFT 大幅下降。但缓存会占 KV/内存，需要淘汰策略。

### 4.6 chunked prefill：用 TTFT 换 TPOT

长 prompt 一次性 prefill 会阻塞 decode。chunked prefill 把 prompt 切成小块，和 decode 交错执行：

- 好处：decode 不被长 prefill 卡住，P95 TPOT 更稳；
- 代价：长 prompt 的 TTFT 可能变长，调度更复杂。

### 4.7 抢占：swap 还是 recompute

KV 不够时，引擎可以：

- **swap**：把 KV 换到 CPU/其他池，等会儿换回来；
- **recompute**：丢掉 KV，重新 prefill；
- **reject/queue**：直接排队或拒绝。

选择取决于 KV 大小、PCIe 带宽、prompt 长度和 SLO。swap 省算力但吃带宽；recompute 省显存但重复算。

## 5. 例子

### 5.1 80 GB 卡，7B，32k

- 权重 14 GB，KV 预算约 64 GiB；
- 每序列 16 GiB → 最多 4 条；
- batch=4 时读取约 $14+4\times16=78$ GiB；2 TB/s 约 39 ms/token；
- 总吞吐约 $4/0.039\approx100$ token/s。

### 5.2 同样 80 GB，8k 上下文

- 每序列 4 GiB → 最多 16 条；
- batch=16 读取约 $14+16\times4=78$ GiB；同样约 39 ms/token；
- 总吞吐约 $16/0.039\approx410$ token/s。

**上下文从 32k 降到 8k，吞吐约 4 倍**；这不是模型变快，是同样显存能装更多序列。

### 5.3 前缀缓存

2k prompt，完整 prefill 1 s；命中率 90% → 约 0.1 s；TTFT 从 1 s 降到 0.1 s。若 100 个请求共享同一段 1.8k 的 system prompt，收益非常明显。

### 5.4 场景闭环：64 并发、32k、80 GB

**输入**：64 个请求，平均 32k prompt、200 输出；80 GB 卡；SLO 是 P95 TTFT ≤ 5 s、TPOT ≤ 100 ms。

**计算**：每条 16 GiB KV，最多 4 条同时驻留；64 条要分 16 批；每批 prefill 32k + decode 200，粗算每批 20 s，总时长 > 5 分钟。**单卡不可能满足 SLO。**

**决策**：① 降上下文到 8k（4 GiB/条，16 条同时）仍不够；② 多卡/多机 + vLLM/SGLang；③ 做前缀缓存 + 摘要/检索，减少 prompt；④ 对长文请求单独队列/降级。

**失败条件**：只加 `--max-num-seqs` 不加卡，KV 会 OOM/抢占；只加卡不做前缀缓存，重复 prefill 仍浪费；只看 GPU 利用率，会误判“还有余量”。

## 6. 常见误区

1. **“batch 越大吞吐越高”**  
   超过 KV 预算会抢占/换出，吞吐反而下降；TPOT 也会变长。

2. **“GPU 利用率高 = 服务好”**  
   利用率高可能是排队/重算；要看 P95/P99 和 goodput。

3. **“PagedAttention 让计算更快”**  
   它主要减少 KV 碎片、提高驻留序列数；单请求 FLOPs 不变。

4. **“prefix cache 一定命中”**  
   前缀必须完全一致；动态 system prompt/时间戳会让命中率归零。

5. **“加卡就能解决并发”**  
   还要看 TP/PP 通信、KV 分片、调度和网关；单请求延迟不一定改善。

## 8. 通往大模型

**出现位置**：[vLLM](#ref-vllm-docs-2026) 的 scheduler/block manager、[SGLang](#ref-zheng-2023) 的 radix tree、[llama.cpp](#ref-llamacpp-server-2026) 的 slot/continuous batching、API 网关的限流。

**形状**：KV 被切成 `[num_blocks, block_size, H_kv, d_k]`；请求到 block 的映射是一张表。

**为什么需要**：不懂调度，你会把“排队”当成“模型慢”，把“KV 不够”当成“GPU 不行”，把“前缀没命中”当成“模型质量差”。

**可检验结论**：32k/80 GB 最多约 4 条 7B 序列同时驻留；把上下文降到 8k，最多约 16 条，吞吐约 4 倍。这个结论用 KV 公式就能算，不需要跑 benchmark。

实用参数：

```bash
# vLLM：并发、上下文、显存、前缀缓存
vllm serve model --max-model-len 32768 --max-num-seqs 8 \
  --gpu-memory-utilization 0.9 --enable-prefix-caching

# llama.cpp：slot 与连续批处理
llama-server -m model-Q4_K_M.gguf -c 32768 -np 4 --cont-batching
```

一个 4 行的并发估算器：

```python
def max_seqs(kv_gib, layers=32, kv_heads=32, dk=128, ctx=32768, bytes_per=2):
    per_seq = 2 * layers * kv_heads * dk * ctx * bytes_per / 2**30
    return per_seq, int(kv_gib // per_seq)

print(max_seqs(64))  # (16.0, 4)
```

## 9. 练习

1. 7B、32k、FP16 KV，80 GB 卡、KV 预算 64 GiB。最多几条序列？每条 KV 多少 GiB？
2. 同样条件，上下文降到 8k，最多几条？吞吐大约几倍？
3. 10 req/s、平均延迟 5 s，系统里平均多少请求？如果 KV 只能驻留 8 条，会发生什么？
4. prefix cache 命中率 90%，完整 prefill 2 s。TTFT 大约从多少降到多少？
5. 64 并发、32k、单张 80 GB 卡，SLO 是 P95 TTFT ≤ 5 s。你会先改什么？为什么不是先加 `--max-num-seqs`？

<details>
<summary>参考答案</summary>

1. 每序列 16 GiB；最多 4 条。
2. 每序列 4 GiB；最多 16 条；吞吐约 4 倍（同样读取量下）。
3. $L=10\times5=50$ 条；8 条驻留意味着大量排队/换出/超时。
4. 从 2 s 降到约 0.2 s（忽略排队/其他开销）。
5. 先降上下文/做摘要与前缀缓存、再考虑多卡；`--max-num-seqs` 只改调度上限，不改 KV 预算，硬开会 OOM/抢占。

## 10. 一页速记

- 并发 = 到达率 × 延迟（Little 定律）；KV 预算决定同时驻留条数。
- batching 摊薄权重，但 TPOT 随 batch 和 KV 变长；存在最优点。
- PagedAttention 省碎片，prefix cache 省重复 prefill；两者都不改变单请求 FLOPs。
- 长 prompt 用 chunked prefill 保护 decode 的 P95；KV 不够时 swap/recompute/queue 三选一。
- 生产看 goodput 和 P95/P99，不看平均吞吐或 GPU 利用率。
