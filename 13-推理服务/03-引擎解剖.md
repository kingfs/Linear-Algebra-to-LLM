# 13.3 引擎解剖：从请求到 token

> **本节位置**：模块 13 · 从模型到服务 ｜ **前置**：[13.1 推理的数学](01-推理的数学.md)、[13.2 模型格式与量化](02-模型格式与量化.md) ｜ **预计**：50 分钟
>
> **一句话**：引擎不是“把模型包一层 HTTP”，而是把 **tokenize → 排程 → prefill → decode 循环 → detokenize** 串成一条可并发、可计费、可观测的流水线。

## 0. 场景引入

你在终端里敲下：

```bash
curl http://127.0.0.1:8080/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"lfm3","messages":[{"role":"user","content":"用三句话解释 KV Cache"}],"max_tokens":200}'
```

0.8 秒后，第一个字出现；4 秒后，200 个 token 生成完。你看到的是“模型在写字”，但在这 4 秒里，引擎做了很多事：

1. 把 JSON 里的消息套进 chat template；
2. tokenize 成 `[B,T]` 的 id；
3. 找到/分配一个 slot，检查 KV 还有没有空间；
4. prefill 整段 prompt，写入 KV；
5. 进入 decode 循环：采样一个 token、追加 KV、再前向；
6. 处理 stop/EOS，detokenize，流式返回。

同样一个请求，llama.cpp、vLLM、Strata 的内部路径完全不同：

- llama.cpp 更像“单机多 slot 的 C++ 服务”，简单、可控、上下文管理透明；
- vLLM 更像“GPU 上的操作系统”，用调度器和 PagedAttention 管很多请求；
- Strata 更像“模型专用的内存编排器”，把专家放在 VRAM/RAM/SSD 三层。

**问题**：为什么 llama.cpp 单用户很快，vLLM 多用户吞吐高，Strata 能跑百B MoE？答案不在一句“kernel 更快”，而在它们**怎么组织这条流水线**。

## 1. 直觉

把引擎想成一家餐厅的后厨：

- **tokenizer** 是前台，把客人的话翻译成厨房能懂的订单（token）。
- **chat template** 是菜单格式，决定 system/user/assistant 怎么排。
- **scheduler** 是传菜员，决定先做哪桌、能不能拼桌。
- **prefill** 是一次性把整桌菜备齐；**decode** 是一道一道上菜。
- **KV Cache** 是已经切好的配菜，放在灶台（VRAM）上，随取随用。
- **detokenizer** 是摆盘，把 token 变成人话。

一条请求的生命周期：

```text
JSON -> chat template -> tokenize -> schedule -> prefill -> decode loop -> detokenize -> SSE
                                      |            |
                                      v            v
                                   KV 分配      采样/停止
```

> 💡 **一句话直觉**：**引擎的差别，主要是“谁来决定顺序、谁管理 KV、谁负责把模型放进内存”。**

这个类比在哪里失效：餐厅的菜可以提前做好，token 不能；餐厅拼桌不会改变菜量，batching 会改变每 token 的权重读取；餐厅的仓库是静态的，引擎的 KV 会随对话增长。

## 2. 定义

### 2.1 引擎的六个部件

| 部件 | 职责 | 典型实现 |
| --- | --- | --- |
| Tokenizer | 文本 ↔ token id | BPE/SentencePiece，GGUF 里带词表 |
| Chat template | 多轮消息 → 一段 prompt | Jinja/Go template，模型卡定义 |
| Model loader | 读权重、分配后端 | GGUF/safetensors/`.ninfer` |
| KV manager | 分配/回收/共享 KV | slot、PagedAttention block、prefix cache |
| Scheduler | 决定 batch、顺序、抢占 | 单队列、continuous batching、优先级 |
| Sampler | logits → token | temperature/top-p/top-k/DRY |

### 2.2 请求、序列、slot

- **request**：一次 HTTP 调用。
- **sequence**：一条 token 流；一个 request 通常对应一个 sequence。
- **slot**：引擎里能独立持有 KV 的“座位”；llama.cpp 的 `--parallel` 就是 slot 数。

一个 slot 同时只能服务一个 sequence（除非共享前缀）。slot 的 `n_ctx` 决定这条序列最多能看到多少 token。

### 2.3 两个阶段

- **prefill**：把 prompt 的 $T$ 个 token 一起过模型，计算密集。
- **decode**：每次 1 个 token，读权重 + KV，带宽密集。

引擎的调度器主要在 decode 阶段做文章：把多个 sequence 的 decode 拼成一个 batch，摊薄权重读取。

## 3. 为什么这样定义

因为“模型”和“服务”是两件事：

- 模型只定义 `forward(tokens, kv) -> logits`；
- 服务要处理并发、排队、KV 碎片、超时、取消、流式、计费、日志。

把引擎拆成六个部件，才能回答：

- 为什么 Ollama 的 `num_ctx` 会影响复读？（KV manager + 截断）
- 为什么 vLLM 的 batch 能开很大？（PagedAttention + 调度）
- 为什么 Strata 能跑百B MoE？（model loader + 专家缓存）
- 为什么 llama.cpp 的 `--parallel` 不是越大越好？（slot × KV）

**引擎的“聪明”，是把模型能力映射到有限资源上。** 只改 kernel 不改调度，通常只能拿到局部收益。

## 4. 性质与推导

### 4.1 请求延迟的分解

$$
T_{\text{request}} \approx T_{\text{queue}} + T_{\text{prefill}} + N_{\text{out}}\cdot \text{TPOT} + T_{\text{detok}}
$$

- $T_{\text{queue}}$：排队等 slot/GPU；
- $T_{\text{prefill}}$：读 prompt；
- $N_{\text{out}}\cdot\text{TPOT}$：逐 token 生成；
- $T_{\text{detok}}$：detokenize/网络，通常很小。

**优化要先看哪一项最大。** 单用户长输出，瓶颈通常是 TPOT；多用户，瓶颈可能是 queue 或 KV 容量。

### 4.2 llama.cpp：slot + 统一 KV + 上下文管理

[llama.cpp 的 `llama-server`](#ref-llamacpp-server-2026) 把模型放在一个进程里，维护若干 slot：

- `-c/--ctx-size`：总上下文；
- `-np/--parallel`：slot 数；
- `-b/--batch-size`、`-ub/--ubatch-size`：prefill 的批大小；
- `--cont-batching`：连续批处理；
- `--kv-unified`：多个 slot 共享一个 KV 池；
- `--cache-type-k/v`：KV 精度；
- `--context-shift` / `--no-context-shift`：上下文满了是否丢前文。

它的代码路径相对直接：请求进来 → 找 slot → tokenize/比较 prefix → prefill 未缓存部分 → decode。日志里能看到 `slot context shift`、`n_ctx`、`n_past` 等。

**适合**：单机、1–2 用户、要控制上下文/采样/日志、CPU/GPU 混合。
**不适合**：几十个并发、需要精细公平性和多卡扩展。

### 4.3 vLLM：调度器 + PagedAttention + 执行器

vLLM 把服务拆成：

- **API server**：HTTP/OpenAI 兼容；
- **scheduler**：决定哪些 request 进入 running batch；
- **block manager**：用固定大小 block 管理 KV（[PagedAttention](#ref-kwon-2023)）；
- **worker/executor**：在 GPU 上跑模型；
- **model runner**：组织 batch、采样。

请求状态通常是 `waiting → running → finished`；显存不够时可能 `swapped`/`preempted`。PagedAttention 让 KV 不必连续分配，减少碎片；prefix caching 复用相同前缀的 block。

**适合**：多用户、RAG、高吞吐、TP/PP。
**代价**：调度复杂、单请求延迟不一定低、配置项多。

### 4.4 SGLang：RadixAttention + 前端/后端

[SGLang](#ref-zheng-2023) 用 radix tree 管理前缀，把共享的 system prompt/RAG 文档缓存下来；前端负责解析结构化程序，后端负责调度和 GPU 执行。对“大量请求共享同一前缀”的场景，前缀命中率会非常高。

**适合**：Agent、RAG、多轮对话、结构化输出。
**代价**：前缀不共享时，收益下降；生态/模型覆盖比 vLLM 窄。

### 4.5 Strata：模型专用 + 三层内存

[Strata](#ref-strata-2026) 不是通用引擎，它把 Qwen3.8-Flash-Next 这类 MoE 拆成：

- **VRAM**：attention/DeltaNet、router、shared experts、output head、MTP draft、热专家缓存；
- **RAM**：全部专家，CPU 用 AVX-512/AVX2 计算未上 GPU 的专家；
- **SSD**：n-gram 表，按 token 读少量行。

它的“引擎”更像一个**内存编排器**：GPU 和 CPU 并行，专家缓存随对话自适应，MTP 一次验证多个 token。

**适合**：12–24 GB 显卡 + 64 GB 内存跑百B MoE。
**代价**：只支持少数模型；项目年轻；速度受 RAM/SSD 带宽限制。

### 4.6 NInfer：单模型、单/双卡、CUDA Graph

[NInfer](#ref-ninfer-2026) 为 RTX 5090/DGX Spark 的少数模型编译：

- 私有 `.ninfer` artifact（权重、配置、tokenizer、模板）；
- CUDA Graph 捕获 decode；
- MTP/DFlash 投机；
- FP8 KV、Vision、TP2/EP2；
- 一个 engine 服务一个模型，最多 8 个活跃请求。

**适合**：硬件/模型正好匹配，追求单卡/双卡极限。
**代价**：Linux only、私有格式、模型覆盖窄。

### 4.7 一张对照表

| 维度 | llama.cpp | vLLM | SGLang | Strata | NInfer |
| --- | --- | --- | --- | --- | --- |
| 核心 | slot + 统一 KV | 调度器 + PagedAttention | RadixAttention | 专家缓存 + 三层内存 | 单模型 CUDA Graph |
| 强项 | 单机可控 | 多用户吞吐 | 共享前缀 | 百B MoE 消费级 | 单/双卡极限 |
| 弱项 | 高并发 | 单请求延迟/配置复杂 | 前缀不共享时收益低 | 模型窄 | 模型/硬件窄 |
| KV 管理 | slot/统一池 | block | radix tree | 分层 | 固定池 |
| 典型用户 | 本地开发者 | 生产 API | RAG/Agent | 研究/极客 | 5090/Spark 用户 |

## 5. 例子

### 5.1 一次 7B 请求的账

7B、2k prompt、200 输出、24 GB 卡、llama.cpp：

- prefill 2k token，按 2,000 token/s 约 1 s；
- decode 200 token，按 50 token/s 约 4 s；
- 总延迟约 5 s，TTFT 约 1 s。

如果 prompt 是 32k，prefill 可能到 16 s，KV 占 16 GiB；这时“首 token 慢”是 prefill，不是 decode。

### 5.2 vLLM 的 64 并发

同样的 7B，8k 上下文，KV 每序列约 4 GiB；80 GB 卡扣掉权重/激活，KV 预算约 64 GiB，最多约 16 条序列同时驻留。vLLM 会把这些序列的 decode 拼 batch，吞吐上升，但单请求 TPOT 变长；超出 KV 预算的请求排队或抢占。

**所以“64 并发”不等于“64 条同时 decode”**；它等于“64 条在系统里，按 KV 和调度逐步推进”。

### 5.3 Strata 的一次 MoE token

百B MoE，每 token 激活 5B 参数，4-bit 约 2.5 GB 活跃权重：

- 热专家在 VRAM：GPU 直接算；
- 冷专家在 RAM：CPU 算，和 GPU 并行；
- n-gram 表在 SSD：每 token 读几行。

如果热专家命中率高，decode 可以到几十 token/s；如果每 token 都缺专家，速度会被 PCIe/内存带宽拖到个位数。

### 5.4 场景闭环：同一个模型，三种引擎

**输入**：7B Q4，24 GB 卡，32k 上下文；需求 A 是单人聊天，需求 B 是 10 人内网 API，需求 C 是 100 人 RAG。

**计算**：A 的 KV 16 GiB，单序列可跑；B 的 10 条序列需要 160 GiB KV，24 GB 卡不可能同时驻留；C 更不可能。

**决策**：A 用 llama.cpp/Ollama；B 降上下文/量化 KV 或换 80 GB 卡 + vLLM；C 必须多卡/多机 + vLLM/SGLang，并做前缀缓存。

**失败条件**：把 B 直接塞进 llama.cpp 的 `--parallel 10`，会因 KV 不足频繁 shift/排队；把 A 放进 vLLM，单请求延迟可能更差。**引擎要和负载匹配，不是越“生产级”越好。**

## 6. 常见误区

1. **“引擎 = 模型”**  
   模型只定义 forward；引擎还管 tokenize、KV、调度、采样、API。换引擎可能改变延迟/吞吐，但不改变模型权重的能力。

2. **“server = engine”**  
   `llama-server` 是 llama.cpp 的服务层；Ollama 是编排层；vLLM 的 API server 只是它的一部分。

3. **“batch 越大越好”**  
   batch 提高吞吐，但会增加 TPOT、KV 压力和排队；超过 KV 预算会抢占/交换。

4. **“PagedAttention 让矩阵乘更快”**  
   它主要减少 KV 碎片、提高驻留序列数；单请求的数学没变。

5. **“模型专用引擎只是 kernel 更快”**  
   Strata/NInfer 的核心是内存编排、专家缓存、投机解码和安装体验，不只是某个 GEMM。

## 8. 通往大模型

**出现位置**：所有推理服务的请求路径；`llama-server` 的 slot、vLLM 的 scheduler、SGLang 的 radix tree、Strata 的 expert cache。

**形状**：请求进来是 `[B,T]` 的 token id；prefill 后 KV 是 `[L,2,H_kv,T,d_k]`；decode 每步追加 1 个位置。

**为什么需要**：不懂引擎，你会把“排队”当成“模型慢”，把“KV 碎片”当成“显存泄漏”，把“前缀没命中”当成“模型质量差”。

**可检验结论**：同一个 7B/32k 请求，在 llama.cpp 上 TTFT 约等于 prefill 时间；在 vLLM 上如果排队，TTFT 可能远大于 prefill。看日志/指标里的 `queue time` 与 `prefill time` 就能区分。

实用命令：

```bash
# llama.cpp：看 slot/上下文/批
llama-server -m model-Q4_K_M.gguf -c 32768 -np 1 --verbose

# vLLM：限制并发与上下文，观察指标
vllm serve model --max-model-len 32768 --max-num-seqs 8 --gpu-memory-utilization 0.9

# 请求侧：看 TTFT/TPOT（流式时间戳）
curl -N http://127.0.0.1:8080/v1/chat/completions -d @request.json
```

一个 5 行的延迟分解器：

```python
def latency(queue_ms, prefill_ms, out_tokens, tpot_ms, detok_ms=2):
    return queue_ms + prefill_ms + out_tokens * tpot_ms + detok_ms

print(latency(0, 1000, 200, 20))  # 5.0 s
```

1. tokenize → chat template → schedule → prefill → decode loop → detokenize/SSE；单用户长 prompt 通常是 prefill，多用户可能是 queue。
2. 不完全一样：llama.cpp 的 slot 更像固定座位 + 统一 KV 池；vLLM 用 block 管理 KV、调度器动态组 batch，支持抢占/前缀缓存。
3. 7B/32k KV 约 16 GiB/序列；10 条需要 160 GiB，24 GB 卡放不下，会 OOM 或频繁 shift。

## 10. 一页速记

- 引擎六部件：tokenizer、template、loader、KV manager、scheduler、sampler。
- 延迟 = 排队 + prefill + 输出 token × TPOT + detokenize。
- llama.cpp 强在单机可控；vLLM 强在多用户吞吐；SGLang 强在共享前缀；Strata/NInfer 强在模型专用。
- batch 提高吞吐但增加 TPOT/KV 压力；PagedAttention 省碎片，不改变单请求数学。
- 引擎要和负载匹配：A 聊天、B 内网 API、C 百人 RAG 是三套不同的账。
