# 13.1 推理的数学：吞吐、延迟与显存

> **本节位置**：模块 13 · 从模型到服务 ｜ **前置**：[11.7 KV Cache](../11-大模型专题/07-KVCache.md)、[11.9 量化](../11-大模型专题/09-量化.md)、[11.10 MoE](../11-大模型专题/10-MoE路由.md)、[12.4 研究路线](../12-进阶/04-研究路线.md) ｜ **预计**：45 分钟
>
> **一句话**：推理服务的“快”不是一句口号，而是三个可算的量：**放得下（显存）、搬得快（带宽）、算得动（算力）**。

## 0. 场景引入

你有一张 24 GB 显卡、64 GB 内存。面前有三个任务：

1. 用 7B 模型做本地聊天，上下文 32k；
2. 用 LFM3-1.7B 做长文档问答，上下文 128k；
3. 用 Qwen3.8-Flash-Next 这类百B MoE 做代码 Agent，权重 100 GB 起步。

直觉会说：7B 和 1.7B 都很小，24 GB 肯定够；百B MoE 太大，肯定跑不了。但真实情况经常反过来：

- 7B 模型在 32k 上下文下，KV Cache 可能就占 16 GiB；如果并发 4 路，64 GiB 直接爆卡。
- LFM3-1.7B 在 128k 上下文下，权重加 KV 也只有 2–3 GB；它复读不是因为“显存放不下”，而是运行时只给了 32k 上下文。
- 百B MoE 反而能在 24 GB 卡上跑：每个 token 只激活几 B 参数，专家放 RAM/SSD，GPU 只算活跃部分。

**同一个“24 GB”，三种完全不同的瓶颈。** 这一节要做的，是把“感觉跑不动”变成一张可以手算的账单。

## 1. 直觉

把推理服务想成一家餐厅：

- **GPU** 是厨房，负责真正做菜（矩阵乘、attention）。
- **VRAM** 是灶台，放当前要用的锅（权重、KV、激活）。
- **RAM** 是仓库，放暂时不用的食材（冷专家、部分权重）。
- **SSD** 是更远的冷库，放很少用的东西（超大 MoE 的专家、n-gram 表）。
- **调度器** 是服务员，决定先做哪桌、拼不拼桌（batching）。
- **API** 是菜单，决定客人怎么点菜（OpenAI/Anthropic 兼容）。

对应到推理，只有三个基本约束：

1. **放得下**：权重 + KV + 激活 ≤ 可用显存；
2. **搬得快**：每生成一个 token，要读的字节数 ÷ 带宽；
3. **算得动**：prefill 的大矩阵乘，要的 FLOPs ÷ 算力。

> 💡 **一句话直觉**：decode 主要不是“算”出来的，是“搬”出来的；谁读的字节少，谁就快。

这个类比在哪里失效：餐厅的菜可以提前做好，token 不能；餐厅加桌子不改变菜量，推理加 batch 会改变每 token 的权重读取摊薄；餐厅的仓库是静态的，推理的专家缓存会随对话变化。

## 2. 定义

### 2.1 引擎、服务、运行时、编排

| 层 | 负责什么 | 例子 |
| --- | --- | --- |
| 引擎（engine） | 前向、采样、KV 管理 | [llama.cpp](#ref-ggerganov-2023)、vLLM、[Strata](#ref-strata-2026)、NInfer |
| 服务（server） | HTTP/OpenAI/Anthropic API、队列、流式 | `llama-server`、vLLM server、NInfer serve |
| 运行时（runtime） | 设备内存、kernel、并行 | CUDA、ROCm、Metal、Vulkan |
| 编排（orchestrator） | 模型管理、路由、扩缩容 | Ollama、Kubernetes、Ray Serve、llm-d |

这四个词经常被混用。**Ollama 是编排层，不是“另一个数学引擎”**：对 GGUF 模型，它会把请求交给 `llama-server`。

### 2.2 四个指标

| 指标 | 含义 | 谁在意 |
| --- | --- | --- |
| TTFT | 首 token 延迟（prefill 为主） | 聊天、代码补全 |
| TPOT / ITL | 每输出 token 延迟（decode 为主） | 流式阅读、Agent |
| 吞吐 | 每秒总 token 数（可含并发） | API 服务、批量任务 |
| goodput | 满足 SLO 的有效吞吐 | 生产 |

**吞吐高不等于延迟低。** batching 能提高吞吐，但会让单个请求的 TPOT 变长；反过来，单请求低延迟的配置，GPU 利用率可能很低。

### 2.3 算术强度与 Roofline

$$
\text{arithmetic intensity}=\frac{\text{FLOPs}}{\text{bytes}}
$$

GPU 的“算力/带宽比”决定屋脊点。算术强度低于屋脊点时，性能由带宽封顶；高于屋脊点时，由算力封顶。

7B fp16 模型 decode 的算术强度大约是：

$$
\frac{2N}{2N\cdot 2\ \text{B}}\approx 0.5\ \text{FLOP/B}
$$

（$N=7\times10^9$，每个参数一次乘加算 2 FLOP，fp16 每参数 2 B。）而 H100 级别的屋脊点约几百 FLOP/B。**decode 离屋脊点差两个数量级，所以它几乎必然是带宽受限的。**

## 3. 为什么这样定义

因为推理的瓶颈会随阶段和负载变化：

- **prefill**：$T$ 个 token 一起过模型，是大 GEMM，计算密集；
- **decode**：每次只来 1 个 token，是瘦 GEMM，带宽密集；
- **长上下文**：KV Cache 显存和读取量随 $T$ 线性增长；
- **高并发**：batching 与 KV 管理决定吞吐；
- **大 MoE**：总参数大，但每 token 只读活跃专家，瓶颈变成“专家放在哪”。

如果只按 FLOPs 做规划，会把 decode 算成“很便宜”：

- prefill 2048 token 的 7B 前向约 $2\times7\times10^9\times2048\approx2.9\times10^{13}$ FLOP；按有效 500 TFLOP/s 算约 58 ms，摊到每 token 约 0.028 ms。
- decode 每 token 也是约 $1.4\times10^{10}$ FLOP，但只为 1 个 token 读 14 GB 权重；按 2 TB/s 算约 7 ms。

**每 token 的 FLOPs 差不多，时间却差 250 倍**，差别在“一份权重喂多少 token”。只盯 FLOPs，就会去优化 prefill 的矩阵乘，而用户真正等待的是 decode。

## 4. 性质与推导

### 4.1 decode 的字节账单

每生成一个 token，至少要读：

$$
B_{\text{decode}} = W + KV_{\text{read}} + B_{\text{act}}
$$

- $W$：权重字节数（量化后）；
- $KV_{\text{read}}$：当前序列要读的 KV 字节数；
- $B_{\text{act}}$：激活、临时缓冲，通常远小于前两项。

理论 TPOT 下限：

$$
\text{TPOT}_{\min}\approx \frac{B_{\text{decode}}}{\text{HBM bandwidth}}
$$

理论单请求吞吐上限：

$$
\text{tokens/s}\approx \frac{\text{HBM bandwidth}}{B_{\text{decode}}}
$$

### 4.2 KV Cache 的形状

对标准多头/GQA 模型：

$$
KV = 2\cdot L\cdot H_{kv}\cdot d_k\cdot T\cdot b
$$

- 2：K 和 V 各一份；
- $L$：层数；
- $H_{kv}$：KV 头数（GQA 后小于 $H$）；
- $d_k$：每头维度；
- $T$：保留的 token 数；
- $b$：每元素字节数（fp16 为 2）。

**7B 例子**（$L=32,H_{kv}=32,d_k=128$，fp16）：

$$
2\cdot32\cdot32\cdot128\cdot2=524{,}288\ \text{B/token}=0.5\ \text{MiB/token}
$$

- 32k：$0.5\times32768=16{,}384$ MiB = **16 GiB**；
- 128k：**64 GiB**。

**LFM3-1.7B 例子**（6 层 global + 5 层 SWA，$H_{kv}=4,d_k=128$，窗口 256，fp16）：

- global 部分：$2\cdot6\cdot4\cdot128\cdot2=12{,}288$ B/token；
- SWA 部分最多保留 256 token：约 2.5 MiB，基本恒定；
- 32k：约 **386.5 MiB**；128k：约 **1.5 GiB**。

同样是“32k 上下文”，7B 要 16 GiB，LFM3 只要 0.38 GiB。**上下文长度的代价，取决于模型结构，不只看 token 数。**

### 4.3 batching 改变的是吞吐，不是单请求延迟

设 batch 为 $B$，每 token 读取：

$$
B_{\text{decode}}(B)\approx W + B\cdot KV_{\text{per-seq}}
$$

权重 $W$ 被 $B$ 个请求摊薄，所以总吞吐上升；但每个请求仍要等自己的 KV 读完，TPOT 可能变长。连续批处理（continuous batching）让新请求在旧请求 decode 之间插入，提高 GPU 利用率。

[PagedAttention](#ref-kwon-2023) 把 KV 分成固定大小的 block，减少碎片；[SGLang](#ref-zheng-2023) 的 RadixAttention 进一步复用共享前缀。它们解决的是“显存利用率/前缀复用”，不是“让单请求的数学变简单”。

### 4.4 量化的收益边界

量化减少 $W$ 和/或 $KV$ 的字节，但不减少 FLOPs。**只有当瓶颈是带宽/显存时，收益才明显。**

一个粗略上界：

$$
\text{speedup}\le \frac{W+KV}{W/q_w+KV/q_{kv}}
$$

- 4k 上下文、7B：$W=14$ GiB，$KV=2$ GiB；KV 量化 2× 只省 1 GiB，上限 $15/14\approx1.07$ 倍。
- 128k 上下文、7B：$W=13$ GiB，$KV=64$ GiB；KV 量化 2× 省 32 GiB，上限 $77/45\approx1.71$ 倍。

**同一个“2× 压缩”，短上下文只值 7%，长上下文值 71%。** 把压缩率当加速比，是推理优化里最常见的空头支票。

### 4.5 MoE：总参数大，但每 token 只读一部分

对 MoE：

$$
B_{\text{decode}}\approx W_{\text{shared}}+W_{\text{active experts}}+KV
$$

- 总参数决定“放哪”（VRAM/RAM/SSD）；
- 活跃参数决定“每 token 读多少”；
- 专家缓存命中率决定“有多少专家要临时搬运”。

如果活跃专家能放进 VRAM，MoE 可以很快；如果放不下，就要靠 CPU/SSD 流式，速度受 PCIe/磁盘带宽限制。**Strata 这类引擎的核心，就是让“活跃专家尽量在 GPU，冷专家在 RAM/SSD”。**

### 4.6 模型专用引擎什么时候赢

模型专用引擎通常在以下条件同时成立时赢：

1. 模型结构固定，能做算子融合/专用 kernel；
2. 硬件固定，能吃透显存/带宽/寄存器；
3. 内存层级复杂（MoE/长上下文/SSD），通用引擎没有为它调；
4. 你接受“只支持少数模型/系统”。

如果只是 1–30B dense 模型、单机低并发，通用引擎（llama.cpp/Ollama）通常更稳，差距也没有宣传的那么大。

## 5. 例子

### 5.1 手算：7B 模型的 decode 上限

7B fp16 权重约 14 GB，HBM 带宽 2 TB/s：

$$
\text{TPOT}_{\min}\approx \frac{14\ \text{GB}}{2000\ \text{GB/s}}=7\ \text{ms}
$$

单请求上限约 $1000/7\approx143$ token/s。加上 32k KV（16 GiB），读取总量 30 GiB：

$$
\text{TPOT}\approx \frac{30}{2000}=15\ \text{ms}\Rightarrow 67\ \text{token/s}
$$

这就是为什么“7B 很快”在长上下文下会打对折：不是模型变慢，是要读的 KV 变多。

### 5.2 诊断：LFM3 的 32k 复读

LFM3-1.7B Q4 权重约 1.1 GB；32k KV 约 0.38 GiB；总占用约 1.5 GB。24 GB 卡完全放得下。

所以 32k 复读**不是显存不够**，而是运行时只给了 32k 上下文（见 [Ollama 文档](#ref-ollama-2026)），超过后截断/context shift。诊断顺序：

```bash
ollama ps
curl -s http://localhost:11434/api/ps | jq '.models[] | {name, context_length, size_vram}'
journalctl -u ollama -n 300 | grep -Ei "truncat|context shift|n_ctx"
```

如果 `context_length` 是 32768，先把 `num_ctx` 提到 64k/128k，并把 `num_keep` 设到 system prompt 长度。具体命令见 [M13 导览](README.md) §13。

### 5.3 选型：同一张 24 GB 卡，三种模型

| 模型 | 权重 | 32k KV | 关键瓶颈 | 推荐 |
| --- | ---: | ---: | --- | --- |
| 7B dense，fp16 | 14 GB | 16 GiB | KV 显存/带宽 | llama.cpp/Ollama；长上下文先量化 KV |
| LFM3-1.7B，Q4 | 1.1 GB | 0.38 GiB | 运行时 `num_ctx` | Ollama/llama.cpp；把上下文给够 |
| 百B MoE，4-bit | 50–100 GB | 取决于结构 | 专家放哪/怎么搬 | Strata/colibri/ds4；不是 llama.cpp 直接加载 |

### 5.4 场景闭环：80 GB 卡上的 7B 长上下文

**输入**：7B fp16（14 GB），80 GB 卡，128k 文档问答；SLO 是 TPOT ≤ 50 ms，质量不低于 fp16 的 99%。

**计算**：128k KV 约 64 GiB；每 token 读取 $14+64=78$ GiB；按 2 TB/s 约 39 ms。刚好在 SLO 内，但只剩 2 GiB 余量，batch 只能 1。

**决策**：先做 KV int8（64→32 GiB），总读取 46 GiB → 23 ms；再把权重换 int8（14→7 GiB），总读取 39 GiB → 19.5 ms。两步都做，才有余量开 batch=2。

**成本**：每套方案一次长文评测 + 约 1–2 周工程；显存从 78 GiB 降到 39 GiB，才谈得上并发。**失败条件**：① kernel 不支持 int8 KV，理论省一半、实测不变；② 质量在 needle-in-haystack 上掉点，平均分看不出来；③ 只测 tokens/s，不固定 batch/长度，结果不可比。

### 5.5 场景闭环：24 GB 卡上的 LFM3 128k

**输入**：LFM3-1.7B Q4 约 1.1 GB，128k 上下文，24 GB 卡，单用户；SLO 是 TPOT ≤ 50 ms。

**计算**：128k KV 约 1.5 GiB；权重 1.1 GB + KV 1.5 GiB + 激活约 1–2 GiB，总计约 4–5 GB；每 token 读取约 2.6 GB，按 2 TB/s 约 1.3 ms，理论上限很高，实际受 kernel/CPU 影响。

**输出**：显存完全够；把 `num_ctx` 设到 131072、`num_keep` 设到 system prompt 长度，关闭不必要的 context shift；不需要 80 GB 卡。

**成本**：显存约 5 GB，电费/硬件成本远低于换卡；主要成本是调参和验证长文质量。

**失败条件**：① 客户端把 `num_ctx` 固定成 32k；② GGUF 元数据把上下文钳到 32k；③ 混合模型的 context shift 导致复读；④ KV 量化过度导致长文掉点。按 13.6 的诊断顺序逐项排除。

## 6. 常见误区

1. **“参数量小就一定快”**  
   decode 读的是权重 + KV；1.7B 模型在 128k 上下文下，KV 也可能成为大头；百B MoE 每 token 只读活跃专家，反而可能比 dense 7B 快。

2. **“量化一定加速”**  
   量化减少字节，不减少 FLOPs；prefill 算力受限时，反量化还可能变慢。先看瓶颈是带宽还是算力。

3. **“上下文长只是显存问题”**  
   长上下文同时增加 KV 显存和每 token 读取量；即使放得下，TPOT 也会变长。显存、带宽、算力要一起算。

4. **“卡越多越快”**  
   多卡要过通信/并行；单请求低延迟场景，多卡经常不如单卡。先看模型能不能单机放下，再谈分布式。

5. **“模型专用引擎一定更好”**  
   它只在“模型在支持列表 + 硬件匹配 + 你接受窄支持”时更好；跑 1.7B 小模型，通用引擎更稳。

## 8. 通往大模型

**出现位置**：所有推理引擎的调度器、KV 管理、量化格式和 batching。

**形状**：7B 的 KV 是 `[L, 2, H_kv, T, d_k]`；LFM3 的 KV 是 global 层 `[6, 2, 4, T, 128]` 加 SWA 层的固定窗口。

**为什么需要**：没有这套账，你会把“上下文不够”误判成“模型不行”，把“量化”误判成“一定加速”，把“多卡”误判成“一定更快”。

**可检验结论**：7B 在 32k 上下文的 KV 约 16 GiB，LFM3 约 0.38 GiB；前者可能爆卡，后者不会。所以 LFM3 的 32k 复读要先查运行时，而不是先换模型。

一个 5 行的 KV 估算器：

```python
def kv_gib(layers, kv_heads, head_dim, tokens, bytes_per=2):
    # K and V, fp16 by default
    return 2 * layers * kv_heads * head_dim * tokens * bytes_per / 2**30

print(kv_gib(32, 32, 128, 32768))   # 7B, 32k -> 16.0
print(kv_gib(6, 4, 128, 32768) + 2.5/1024)  # LFM3 global + SWA -> ~0.38
```

对应到代码/参数：

- llama.cpp：`-c/--ctx-size` 决定 `n_ctx`；`--cache-type-k/v` 决定 KV 字节；`--no-context-shift` 控制满了是否静默丢前文。
- vLLM：`--max-model-len`、`--gpu-memory-utilization`、`--max-num-seqs` 决定并发与 KV 预算；PagedAttention 管理 block。
- Strata：专家缓存 + RAM/SSD 分层；每 token 只搬活跃专家，n-gram 表从 SSD 读。

## 9. 练习

1. 7B 模型，$L=32,H_{kv}=8,d_k=128$，fp16，上下文 32k。KV 是多少 GiB？和 $H_{kv}=32$ 相比省了多少？
2. LFM3-1.7B，6 层 global（$H_{kv}=4,d_k=128$）+ 5 层 SWA（窗口 256），fp16，128k 上下文。KV 大约多少 GiB？
3. 一张 80 GB 卡，7B fp16（14 GB），128k 上下文。只做 KV int8，TPOT 的理论下限从多少降到多少（按 2 TB/s）？
4. 什么时候选 vLLM，什么时候选 llama.cpp？各举一个负载例子。
5. 有人要在 24 GB 卡上跑 100B MoE。你需要先问哪四个问题？

<summary>参考答案</summary>

1. $2\cdot32\cdot8\cdot128\cdot32768\cdot2/2^{30}=4$ GiB；$H_{kv}=32$ 时是 16 GiB，省了 12 GiB（4 倍）。
2. global：$2\cdot6\cdot4\cdot128\cdot131072\cdot2/2^{30}=1.5$ GiB；SWA 约 2.5 MiB；合计约 1.5 GiB。
3. 读取量从 $14+64=78$ GiB 降到 $14+32=46$ GiB；2 TB/s 下从约 39 ms 降到 23 ms。
4. 多用户/高吞吐/RAG → vLLM；单机 1–2 用户、要控制上下文/采样/日志 → llama.cpp。
5. ① 总参数/活跃参数；② 专家能不能放 RAM、RAM 多大；③ 磁盘带宽/容量；④ 目标 tok/s 与并发。四个都满足，才谈“能跑”。

</details>

## 10. 一页速记

- **decode 是带宽受限**：每 token 读权重 + KV；$ \text{TPOT}\approx B_{\text{decode}}/\text{BW}$。
- **KV 公式**：$2\cdot L\cdot H_{kv}\cdot d_k\cdot T\cdot b$；7B/32k 约 16 GiB，LFM3/32k 约 0.38 GiB。
- **量化收益有边界**：省下的字节 ÷ 总读取字节；短上下文可能只有 7%，长上下文才到 71%。
- **batching 提高吞吐，不一定降低单请求延迟**；PagedAttention/prefix cache 解决显存与前缀复用。
- **先定位瓶颈再选引擎**：放不下、搬得慢、算得动，是三张不同的账单。
